01 · Threat model

Two failure modes explain the whole battery

Wei et al. argue every jailbreak in the battery reduces to one of two root causes in how safety training interacts with the base model.

Failure mode 1

Competing objectives

Pretraining and instruction-following push the model to comply; safety training pushes it to refuse. Attacks that win this tug-of-war exploit the conflict directly.

prefix_injection → force the reply to start with
"Absolutely! Here's" so a refusal can't lead
Failure mode 2

Mismatched generalization

Safety fine-tuning only covers natural-language prompts. Inputs that are in-distribution for pretraining but out-of-distribution for safety data slip past it.

base64 → the harmful request survives in the
base model's knowledge, not in the safety data
02 · Attack battery

The techniques to implement, grouped by mechanism

This is a curated subset of the Wei et al. catalogue. Figures shown are the highest reported BAD BOT rate on GPT-4 or Claude v1.3 from their evaluation, for scale — your own numbers will depend on your target model.

base64 / base64_raw

Encode the request (and optionally decode the reply) so the harmful instruction never appears as natural-language text.

up to 66% BAD BOT
base64_input_only / output_only

Ablations that encode only one side of the exchange, isolating which direction the safety filter actually watches.

rot13

Simple substitution cipher; weak on its own, useful as a combination-attack ingredient.

leetspeak

Character substitution (a→4, e→3 …) that keeps the text human-readable but token-distorted.

disemvowel

Strip vowels from the harmful request to push it outside the safety training distribution.

evil_confidant

Roleplay frame in which the model plays an amoral confidant persona with no restrictions.

AIM

Top-voted jailbreakchat.com persona prompt; effectively a hand-tuned combination attack.

up to 86% BAD BOT (GPT-4)
dev_mode_v2 / dev_mode_with_rant

"Developer mode" framing that claims to unlock an unfiltered output mode.

wikipedia / wikipedia_with_title

Reframes the harmful ask as writing a neutral encyclopedia article on the topic.

poems

Reframes the request as a creative-writing / poetic form.

prefix_injection

Forces the answer to begin with an affirmative string, structurally blocking a refusal opener.

prefix_injection_hello

Ablation with a neutral prefix — confirms the specific chosen prefix is what matters.

refusal_suppression

Explicit instruction never to use refusal language ("cannot", "sorry", "unable").

refusal_suppression_inv

Inverse-phrased ablation, used to isolate the effect of the exact suppression wording.

style_injection_json / _short

Constrains the output format so the model can't produce a long templated refusal.

distractors / distractors_negated

Buries the harmful request among benign ones to dilute the safety objective's attention.

auto_payload_splitting

Uses a helper LLM to flag sensitive tokens, then splits/reassembles them programmatically.

auto_obfuscation

Uses a helper LLM to invent a novel obfuscation of the prompt on the fly.

few_shot_json

Primes the model with compliant-looking example turns before the real request.

combination_1

prefix injection + refusal suppression + base64, stacked in one prompt.

combination_2

combination_1 plus a style-injection constraint on the output format.

combination_3

combination_2 plus a fake "website content" framing — the strongest single attack tested.

up to 94% BAD BOT
adaptive attack

Run the whole battery per prompt; counts as a success if any single member succeeds. This is the project's actual "battery" strategy.

96–100% BAD BOT
03 · Defense stack

Four layers, each catching what the last one misses

No single defense from the papers stops the whole battery. Layering them — and adding your own hardening layer — is the actual design contribution the report is asking for.

1
Jain et al. · Alon & Kamfonas — detection

Perplexity filter (plain + windowed)

Score each prompt's log-perplexity under a scorer model. Reject if it exceeds a threshold calibrated on your own benign set; the windowed variant also scores contiguous chunks so a locally anomalous adversarial suffix can't hide inside an otherwise fluent prompt.

threshold ≈ 997–1000 log-ppl window size ≈ 10 tokens false-positive rate ≈ 6–10%
Blind spot: it's a gibberish detector, not a jailbreak detector. Fluent, human-authored attacks — AIM, roleplay, prefix injection — pass straight through because nothing about their token statistics looks abnormal.
2
Jain et al. — preprocessing

Paraphrase preprocessing

Route every prompt through a second, separate model with a fixed "paraphrase the following sentences:" instruction before it ever reaches the target model, disrupting attacks that depend on an exact, brittle token sequence.

≈15× fewer successful attacks in original study 10–15% benign-quality drop
Blind spot: paraphrasing preserves meaning, so persona/roleplay attacks and distractor framing survive intact. Also only gray-box safe — an attacker with white-box access to the paraphraser can chain optimizers against it.
3
your design — instruction hardening

System-level reinforcement

An explicit instruction-hierarchy reminder and refusal-priming in the system prompt, plus a constrained output schema, aimed squarely at the competing-objectives attacks the first two layers can't see.

Why it's here: this is the piece you design and justify yourselves — it's what the "did you design any countermeasure" report question and the 10% bonus are actually asking for.
4
your design — output-side check

Response classification

Scan the model's own reply for signs of compliance with a harmful request — a lightweight version of the BAD BOT / GOOD BOT / UNCLEAR labeling Wei et al. use to grade attacks — before it ever reaches the user.

Why it's here: a last line of defense for whatever gets through layers 1–3, and it doubles as your automated grader for the evaluation phase of the workflow below.

05 · Workflow

Four sprints, week 10 to week 13 Saturday

With ~3.5 weeks left and both reports due on the same day, there's no room for the old sequence of build-everything-then-write-everything. Build breadth-first, run your one full evaluation pass by the middle of week 12, and write both reports off that single pass. Click a sprint to expand it.

Attack side
  • Pin the target ("victim") model and its exact version/checkpoint today
  • Trim the battery to ~8–10 techniques, one per category — depth later, not now
  • Stub every technique as a function, even crudely, so the harness has something to call
Defense side
  • Pin the perplexity-scorer model and the paraphraser model
  • Stub Layer 1 with the paper's reported threshold as a placeholder — calibrate for real later
  • Stub Layers 2–4 as pass-through functions so the pipeline shape exists end to end
Attack side
  • Finish every technique implementation and the adaptive-attack harness
  • Run a first battery pass against the undefended target for a baseline ASR by Friday
  • Freeze the battery Sunday night — no new techniques after this
Defense side
  • Calibrate the perplexity threshold on your own benign set, replacing the placeholder
  • Finish Layers 2–4 for real and wire all four into one pipeline in front of the target
  • Smoke-test the full pipeline on a handful of prompts by Sunday night
Report side
  • Start the Design Report now: draft the topology diagram and attack definitions from what's already built
  • Don't wait for final numbers — the shape of the report can exist before the data does
Both, by Wed
  • Run the full battery against the full defense stack — per-attack ASR, before and after
  • Measure benign pass-through and quality drop as your cost-of-defense numbers
  • Save every raw transcript now; this is the evidence base for both reports and the demo
Thu–Sun
  • Write first complete drafts of both the Design Report and the Final Report from this one pass
  • Script the live demo and start capturing clean snapshots of attacker/victim output

08 · Team & reproducibility

Split the work, then pin the run

Member A — Attack lead
  • Owns the battery implementation and adaptive-attack harness
  • Owns the harmful-prompt / benign-prompt datasets
  • Owns baseline ASR measurement against the undefended target
Member B — Defense lead
  • Owns Layers 1–2 (perplexity filter, paraphraser)
  • Owns Layers 3–4 (hardening, output check) with joint design input
  • Owns false-positive / quality-drop measurement on the benign set

Reproducibility checklist — pin before your first real run

  • Target model name, provider, and exact version/checkpoint
  • Paraphraser model name and version
  • Perplexity scorer model name and version
  • Random seeds for every stochastic step
  • Frozen harmful-prompt set (with a count)
  • Frozen benign-prompt set (with a count)
  • Library / framework versions (PyTorch, Transformers, etc.)
  • Raw transcripts saved for every attack × defense combination
